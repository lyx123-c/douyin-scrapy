# Update Protocol and Security Foundation (U1.1)

## Scope

This phase defines the version contract, update manifest, Ed25519 trust model, public update source configuration, file path policy, and the local version information contract. It does not download, apply, or roll back updates, and it does not ship an Updater executable.

The production update source is the public GitHub repository `lyx123-c/douyin-scrapy`. The client uses only public Release assets and never embeds a GitHub Token.

## Version Contract

The source of truth is:

- Product and channel: `frontend/update/update-contract.json`
- Package version: `frontend/package.json`
- Git tag and commit: generated by `frontend/scripts/generate-version-metadata.cjs`
- Runtime metadata: `frontend/build/version-metadata.json`

Generated fields:

```json
{
  "schema_version": 1,
  "product_id": "com.local.douyinworkbench",
  "version": "0.2.0",
  "channel": "stable",
  "tag": "v0.2.0",
  "commit": "<git-commit>",
  "build_time": "<ISO-8601 UTC>",
  "updater_version": "0.0.0",
  "build_dirty": false
}
```

`updater_version: 0.0.0` means no Updater executable exists. It will become a real semantic version in U1.2.

Commands:

```powershell
npm run version:metadata
node scripts/generate-version-metadata.cjs --require-release
```

`--require-release` requires a clean worktree and an exact `v<version>` or `<version>` Git tag.

Electron reads the generated metadata, verifies that `version` equals `app.getVersion()`, and passes product/version/channel/tag/commit/updater version to Backend. Backend reports the same values from `/api/health`.

## Manifest

Formal schema: `frontend/update/update-manifest.schema.json`

Top-level fields:

- `schema_version`
- `product_id`, `channel`
- `version`, `tag`, `commit`, `build_time`
- `release_sequence`, `published_at`
- `min_supported_version`, `minimum_updater_version`
- `release_notes`
- `files[]`: complete target inventory with path, size, SHA256 and executable marker
- `changes`: `added`, `replaced`, `removed`
- `packages[]`: full installer, file delta and optional binary delta
- `signatures[]`: Ed25519 signatures over the canonical manifest body

`release_sequence` is monotonic and is used together with version to reject replayed manifests.

Every manifest must include a full installer package. File and binary deltas are accelerators with full-package fallback.

Package types:

- `full`: NSIS installer, `base_version=null`
- `file_delta`: ZIP of changed files, requires exact `base_version`
- `binary_delta`: ZIP plus `delta_algorithm=hpatch`, requires exact `base_version`

## Signature Model

Canonicalization is project canonical JSON v1: UTF-8, no whitespace, object keys sorted lexicographically, arrays preserved, non-JSON values rejected. `signatures` is removed before signing.

Signature algorithm: Ed25519.

Keyring: `frontend/update/keyring.json`

Key statuses:

- `active`: may authenticate a new release
- `retired`: may participate in a rotation signature but cannot authorize a release by itself
- `revoked`: always rejected

Key rotation requires dual signatures from the retired and new active keys. Revoked keys are rejected immediately. `not_before` and `not_after` are optional.

Key operations:

```powershell
node scripts/manage-update-key.cjs generate --key-id release-2026-01 --private-key-out C:\secure\release-2026-01.pem --keyring update\keyring.json
node scripts/manage-update-key.cjs retire --key-id release-2025-01 --keyring update\keyring.json
node scripts/manage-update-key.cjs revoke --key-id release-2025-01 --keyring update\keyring.json
node scripts/sign-update-manifest.cjs --manifest stable-unsigned.json --key release-2026-01=C:\secure\release-2026-01.pem --output stable.json --detached stable.json.sig
```

Private keys must never be committed or packaged.

## Verification Pipeline

`frontend/electron/update/manifest-verifier.cjs` rejects updates when any check fails:

1. Supported schema version.
2. Manifest shape and semantic versions.
3. Ed25519 signatures from known, non-revoked keys.
4. At least one active signing key.
5. Expected product ID and channel.
6. Downgrade detection.
7. Replay detection using version and `release_sequence`.
8. Minimum supported version.
9. Minimum Updater version.
10. File path scope, traversal and duplicate checks.
11. Delete ownership against the installed file inventory.
12. Compatible base package selection.
13. Separate package size and SHA256 verification.

SHA256 verification never substitutes for signature verification.

## Path Policy

Only these manifest scopes are allowed:

- `program/`
- `updater/`

The policy rejects:

- Absolute paths and backslashes
- `.` and `..` segments
- Windows drive and alternate data stream syntax
- Windows reserved device names
- Control characters, trailing dots/spaces and duplicate case-insensitive paths
- Deletion of files absent from the installed signed inventory
- Any path outside `program/` or `updater/`

User data roots, video roots, Cookie/Profile, CSV, queue, logs and the bootstrap storage file are outside the update protocol.

## Public Update Source

Configuration: `frontend/update/update-source.json`

`repository` is configured as `lyx123-c/douyin-scrapy` and explicitly approves this public development repository as the update source. If the repository becomes private or the approval flag is removed, update checks must fail safely.

The client:

- Uses direct GitHub Release asset URLs.
- Does not require GitHub login or a Token.
- Does not use the GitHub API as the only download path.
- Permits only configured HTTPS hosts.
- Rejects credentials in URLs.
- Distinguishes `UPDATE_NETWORK_ERROR`, `UPDATE_SOURCE_NOT_FOUND`, `UPDATE_SOURCE_HTTP_ERROR` and `UPDATE_MANIFEST_INVALID`.

The repository must remain public. A private repository cannot be used for anonymous client updates.

## Local Version Information Interface

Preload exposes only:

```js
window.desktopRuntime.updates.getLocalInfo()
```

The returned contract includes current version, channel, tag, commit, build time, Updater version, update source status and reserved fields for latest version, update status, release notes, package size, update method and minimum Updater version.

No update UI, update check request, download or installation action is implemented in U1.1.

## U1.2 Full NSIS Installer Flow

U1.2 implements full NSIS installer updates only. File-level and binary deltas remain disabled even if present in a manifest.

Flow:

1. Fetch the configured public Manifest.
2. Verify its Ed25519 signatures, product, channel, versions and full-package metadata.
3. Download to a unique `.part` file under the OS temporary update directory.
4. Verify exact size and SHA256.
5. Rename the temporary file to `.exe` only after verification.
6. Before install, verify Backend is idle and Electron owns the process.
7. Call `POST /api/system/prepare-update-shutdown`; FastAPI stops RuntimeServices and schedules uvicorn exit.
8. Electron waits for the Backend process exit, without `taskkill /F`.
9. Electron starts a hidden PowerShell handoff that waits for the Electron PID to exit.
10. The handoff starts the verified NSIS installer with `/S` and no `/D`; the existing installation location is preserved.
11. The handoff waits for installer exit, requires exit code 0 and verifies `resources/version-metadata.json` equals the target version.
12. It writes `update-result.json` and starts the new application with `--post-update`.
13. The new application verifies product/version via Backend Health and reports `UPDATE_SUCCEEDED` or `UPDATE_FAILED` in Settings.

Cancel or failed download removes the `.part` file. SHA256 mismatch never creates a runnable installer.

The renderer can only invoke fixed IPC operations. It cannot provide a URL, filesystem path, command, or executable.
